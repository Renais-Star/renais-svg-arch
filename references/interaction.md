# Interaction · 引导式提问闭环

用户触发 skill 时，输入信息量参差不齐——有人什么都没说，有人只给主题，有人给了完整文档。**不要用一套固定话术应对所有情况**，先判定入口，再走对应的提问路径。

核心原则：**用最少轮次问清必要信息，每个问题给点选选项，回答不充分就暂停（不用默认值硬走）。**

## 第 0 步：判定入口（必做，每次都判）

收到用户消息后，先判断属于哪种情况：

### 入口 A：空白 / 几乎空白

**判定**：消息里**没有任何具体业务词**（如 电商/SaaS/订单/支付/用户中心/数据库/k8s 这种），只有泛泛的"画个架构图""生成架构图""/renais-svg-arch"。

→ 走 **引导模式**

### 入口 B：有主题，但模糊

**判定**：消息里有 **≥1 个业务词**（说明知道要画什么），但**没有模块/层级的具体枚举**（没有"分三层：A、B、C"这种）。

示例：
- "画个电商架构" ✓（有"电商"，无枚举）
- "做个微服务图" ✓
- "我们有个订单系统，画一下" ✓

→ 走 **补充模式**

### 入口 C：详细材料

**判定**：出现了**具体的模块/层级枚举**，或附带 **文件 / 链接 / 长文本（>100 字）/ Markdown**。

示例：
- "我们分四层：接入层有 Web/App，服务层有订单/用户/支付，数据层有 MySQL/Redis"
- [附带 .md 文件]
- 一大段需求文档

→ 走 **抽取模式**

### 判定不清时

如果 A 和 B 难以区分（比如"画个云架构"——"云"算业务词吗？），**按 B 处理**（补充模式更友好，不会让用户觉得被当成完全空白）。

---

## 引导模式（入口 A）

用户不知道要什么。先帮他想清楚"画什么形态"，再要内容。

### 第 1 次：用 AskUserQuestion 选布局

4 个选项，每个选项的 `label` 是布局名，`description` 说清"它表达什么关系 + 适合什么"：

```
question: "你想画哪种架构？"
header: "架构类型"
options:
  - label: "分层架构"
    description: "上层依赖下层。适合技术栈、云平台、系统分层（如：接入层→服务层→数据层）"
  - label: "流程管道"
    description: "数据/请求从左到右流。适合 ETL、数据管道、请求链路（如：采集→处理→存储）"
  - label: "中心辐射"
    description: "一个核心连接多个节点。适合 API 网关、消息总线、IAM 中心（如：网关连各服务）"
  - label: "角色流程"
    description: "谁负责哪一步。适合审批流、工单流转、业务时序（如：用户→审核→执行）"
```

映射关系（AI 内部知道，不用告诉用户）：
- 分层架构 → `layered-stack`
- 流程管道 → `flow-pipeline`
- 中心辐射 → `hub-spoke`
- 角色流程 → `swimlane`

### 第 2 次：用文字问内容（不用 AskUserQuestion）

布局选完后，**内容是开放长文本**，AskUserQuestion 的输入框不适合。直接文字问：

> 好，那就用 [布局名]。请告诉我具体画什么——
>
> 可以是任意形式：一段文字描述（"我们有个订单系统，用户下单后走支付、库存、发货"）、Markdown、或直接贴一段文档。越具体越好，不知道怎么组织也没关系，我会帮你整理。

**这一步是必答**。用户没给实质内容（只说"随便""你看着办"）→ **暂停**：

> 内容我没法替你编——架构图必须基于你的真实系统。哪怕简单几句"我们有什么、它们怎么连"也行。你描述一下，或者如果你有现成文档可以贴过来。

## 补充模式（入口 B）

主题明确，补全范围 + 形式。**一次 AskUserQuestion 问 3 个**（工具支持多 question）：

### 1 次 AskUserQuestion（3 个 question 同时问）

**Q1 范围**（必答）：
```
question: "画多大范围？"
header: "范围"
options:
  - label: "全链路"        description: "端到端，从入口到存储都画"
  - label: "只画某层/某端"  description: "如只画后端服务、只画数据层"
  - label: "突出某模块"     description: "整体简略，某模块（如支付）重点展开"
```

**Q2 风格**（必答）：
```
question: "用哪种视觉风格？"
header: "风格"
options:
  - label: "暗色科技"   description: "dark-tech，青绿紫强调色，赛博朋克感（互联网/科技团队）"
  - label: "亮色清爽"   description: "light-tech，白底，同款强调色（打印/文档嵌入）"
  - label: "政务商务"   description: "civic-blue，蓝色渐变层（政府/国企/正式场合）"
  - label: "黑白论文"   description: "minimal-mono，纯线框无彩色（论文/白皮书/专利）"
```

**Q3 图标**（必答）：
```
question: "模块要带图标吗？"
header: "图标"
options:
  - label: "不要图标"  description: "纯文字模块，更简洁（默认推荐）"
  - label: "要图标"    description: "每个模块配图标，更直观（产品/教学场景）"
```

### 布局怎么定

补充模式**不单独问布局**——从主题词推断，在提问前用一句话告知用户：

> 从你说的"[主题]"看，这更像 [布局名]（因为 [理由]）。如果不对，回复时告诉我。

如果主题实在推断不出布局（比如"画个系统架构"太泛），把它加进 Q1，Q1 改成"布局 + 范围"二合一。

### 问完之后

收到 3 个回答 → 按 structuring.md 抽取（此时信息已够）→ 进入"确认结构"环节（见下文"通用确认点"）。

## 抽取模式（入口 C）

材料够，尽量少问。**分两步**（用户决策：可以分步）。

### 第 1 步：内部抽取 + 确认结构

按 [structuring.md](structuring.md) 抽取（不问用户）。抽完后，用 AskUserQuestion 确认结构：

```
question: "我抽出了这样的结构，对吗？
  - 布局：[X]（理由：[一句]）
  - [N] 层：[列出每层名]
  - 关系：[列出，标注 (默认推断) 的]
  - 侧栏：[如有]"
header: "结构确认"
options:
  - label: "结构没问题"     description: "按这个继续画"
  - label: "有地方要改"     description: "我会告诉你改哪里"
```

用户选"有地方要改" → 文字追问哪里改，改完重新确认。**改不到位不进入下一步。**

### 第 2 步：问形式（结构确认后）

1 次 AskUserQuestion（2 个 question）：

**Q1 风格**（必答）：4 选项（同补充模式 Q2）

**Q2 图标**（必答）：要 / 不要（同补充模式 Q3）

> 布局已经在第 1 步确认过了，这里不再问。

### 问完之后

→ 读参考 → 生成 → 校验。

---

## 通用确认点（三种模式共用）

无论哪种模式，**生成前必须有明确的 structured-content.md**，且结构已确认。这是硬门槛。

如果用户在确认环节表现出犹豫（"差不多吧""你看呢"），**不要默认通过**，反问一个具体点：

> "差不多"的话我按 [当前结构] 画。有一个我不确定的：[具体模块/关系]，你确认下是 A 还是 B？

把模糊确认转成一个具体的小问题。

---

## 暂停规则（硬性，三种模式通用）

遇到以下情况，**立即停下，不要用默认值强行生成**：

| 触发 | 应对 |
|------|------|
| AskUserQuestion 用户选"其他"但没填实质内容 | 追问："你选了其他，能具体说说吗？" |
| 用户说"随便/你看着办/都行" | 停："内容我不能替你编，至少告诉我 [最关键的 1 点]" |
| 用户回答自相矛盾 | 停："你前面说 X，现在又说 Y，以哪个为准？" |
| 关键信息缺失（如布局和主题都没有） | 停："需要你先确认 [X] 才能继续" |
| 用户说"先等等/我再想想" | 停："好，想好了告诉我" |

**核心理念**：宁可多问一轮，不要画出用户不想要的东西。一次返工比一次追问代价大得多。

---

## 提问措辞规范

1. **每个 AskUserQuestion 的 option 都带 description** —— 不只给名字，说清"这是什么/适合什么"
2. **不要一次问超过 3 个 question** —— 用户烦
3. **文字提问时给示例** —— "比如 A、B、C 这种"降低理解成本
4. **告知推断理由** —— "我建议 X，因为 Y"，让用户能判断对不对
5. **确认时复述结构** —— 不要让用户回忆，把抽到的结构列出来让他看

---

## 何时不用问（可直接生成）

只有一种情况可以跳过提问直接生成：**用户在初始消息里就明确给出了全部要素**——

- 具体内容（模块/层级）
- 风格（明说"暗色"/"黑白"等）
- 布局（明说"分层"/"泳道"等，或内容强烈暗示）
- 图标偏好（明说"带图标"/"纯文字"）

这种情况罕见。99% 的情况都要走提问闭环。即便如此，生成前也要快速复述一下"我按 [X 风格 + Y 布局 + 带/不带图标] 画了"，给用户一个拦截机会。
