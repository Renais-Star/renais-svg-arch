# Structuring · 从自由文本抽取架构结构

把用户给的杂乱输入（文字 / Markdown / 文档片段 / 会议纪要 / 口述）转成稳定的 `structured-content.md`。

这是整个流程里**最容易出错的一步**——输入形态千变万化，漏抽一层或瞎编一个模块，后面的图就全错。本文给一套确定性方法，让抽取过程可复现、可校验。

## 核心原则

1. **只抽用户明说的，不脑补**：用户没提的模块绝不臆造。不确定就标记 `[待确认]`，不要硬填
2. **结构先行，细节后补**：先把"几层 / 每层几个模块 / 关系"骨架定下来，再补描述
3. **保留原词**：用户说"订单中台"就写"订单中台"，不要自作主张改成"Order Service"
4. **双语标注**：中文为主，英文辅助（用户没给英文就标 `[需补 EN]`，不要瞎翻译）

## 第一步：识别输入类型

不同输入用不同策略：

| 输入类型 | 特征 | 策略 |
|---------|------|------|
| **结构化 Markdown** | 有 `##`/`###` 标题层级、列表 | 直接映射：标题→层/模块，列表项→子模块 |
| **流水账文字** | 一段段描述，无明显层级 | 走"信号词识别"(见下) |
| **需求/设计文档** | 含"系统组成""架构""模块"章节 | 定位架构章节，再走结构化 |
| **会议纪要/口述** | "我们大概分三层，上面是..." | 抓"分层/组成"语句，走信号词识别 |
| **现有架构图描述** | 描述一张图的内容 | 按空间顺序(上→下/左→右)还原结构 |
| **混合输入** | 文字 + 表格 + 代码 | 表格优先(信息最密)，文字补充 |

> 如果输入**完全无关架构**(比如一段产品介绍、用户故事)，停下来问用户："这段内容里我没找到明确的架构/层级信息，能否补充系统组成？"——不要硬抽。

## 第二步：识别层级（信号词法）

从文字里找"分层信号"。这些词**强暗示**前面有一个架构层：

### 中文信号词

| 信号词 | 抽取规则 | 示例 |
|--------|---------|------|
| "分为 N 层" / "N 层架构" | N = 层数，后面跟着是各层 | "分为三层：接入、服务、存储" |
| "上层 / 下层 / 底层" | 上下关系 = 层级 | "下层是数据库" |
| "最上面 / 最下面 / 中间" | 空间隐喻 = 层级顺序 | "最上面是用户端" |
| "X 层 / X 模块 / X 体系" | 后跟的名字就是一个层/模块 | "应用层"、"安全体系" |
| "包括 / 包含 / 由...组成" | 后面的列表是同层并列 | "服务层包括订单、用户、商品" |
| "首先 / 然后 / 最后" | 时序 = 流程步骤(swimlane) | "先提交订单，然后..." |

### 英文信号词

| Signal | Rule |
|--------|------|
| "N-tier", "N-layer", "consists of N layers" | N = layer count |
| "on top of", "underneath", "above", "below" | vertical = layer order |
| "X layer", "X module", "X tier" | the name is a layer |
| "includes / consists of / is composed of" | following list = siblings |
| "first ... then ... finally" | temporal = flow steps |

### 抽取算法

```
1. 扫描全文，标记所有"分层信号词"出现位置
2. 每个信号词触发一次"层抽取":
   - "分为 N 层" → 期待后面有 N 个层名
   - "X 层" → X 是一个层名
3. 按出现顺序排层(先提到的在上/在前)
4. 如果信号词之间有矛盾(如既说"三层"又列了五个)，以枚举清单为准，
   并标记 [层数待确认: 文中说三层但枚举了五个]
```

## 第三步：识别每层内的模块

定位到层后，找该层下的模块：

```
层名 { ... 这段范围内的内容 ... }
```

范围界定规则：
- 如果是 Markdown：从该标题到下一个同级标题之间
- 如果是文字：从该层名到下一个层名之间，或到段落结束

模块抽取规则：
- 列表项（`-` / `*` / 数字列表）→ 每项一个模块
- "包括 A、B、C" / "A, B, C" → 逗号/顿号分隔，每个一个模块
- "A（描述）" / "A: 描述" → A 是模块名，括号/冒号后是描述

**子模块识别**：如果某模块下还有缩进列表，那些是子模块。架构图一般只画到二级（层 → 模块），子模块作为模块的描述文字，不再单独画框——除非用户明确要求三级。

## 第四步：识别关系

关系是最容易漏的。三类关系要分别找：

### 1. 层间依赖（layered-stack 默认）

如果用户描述了"上下"关系但没明说箭头，**默认上层依赖下层**（标准架构图语义）。在 structured-content.md 里写：

```markdown
## Relationships
- 用户层 → 应用层: 默认依赖(用户未明说，按架构图惯例)
- 应用层 → 数据层: 默认依赖
```

并标注 `(默认)`，让用户知道这部分是推断的。

### 2. 显式关系（用户明说）

找这些信号词：

| 信号词 | 关系类型 |
|--------|---------|
| "调用 / 请求 / 访问" | A → B 单向 |
| "返回 / 回调 / 通知" | A → B 单向(反向) |
| "交互 / 通信 / 同步" | A ↔ B 双向 |
| "通过 X" | X 是中间件/总线 |
| "异步 / 消息 / 队列" | 经过消息总线 |
| "缓存 / 读写 / 落盘" | 数据访问关系 |

### 3. 横切关系（侧栏）

如果某些模块"作用于所有层"，它们是侧栏，不是某层的一部分：

| 信号词 | 归类 |
|--------|------|
| "安全 / 鉴权 / 加密 / 审计" | 左侧栏(安全保障) |
| "监控 / 日志 / 告警 / 追踪" | 右侧栏(运维) |
| "标准 / 规范 / 准则" | 底部基座 |
| "贯穿 / 横切 / 所有层 / 全局" | 横切关系 → 侧栏 |

> 这是 civic-blue 风格的核心特征。如果输入里出现这些词，归侧栏而不是主层。

## 第五步：判定布局

根据抽到的结构特征选布局：

```
决策树：
├─ 有明确的"角色/部门/系统"且关注"谁做什么"?
│   └─ Yes → swimlane
├─ 有"中心 + 多个围绕"的特征(网关、总线、IAM)?
│   └─ Yes → hub-spoke
├─ 有"流向/管道/上游下游"且线性?
│   └─ Yes → flow-pipeline
├─ 有"上下分层/依赖"?
│   └─ Yes → layered-stack(默认)
└─ 不确定 → layered-stack(最通用)
```

判定后**向用户确认**，不要默默决定。话术：

> 从你描述的内容看，这更像 [X 布局]，因为 [理由]。你也可以选 [其他布局]，看哪种更贴切？

## 第六步：识别语言与标注

- 检测输入主语言（中/英/混合）
- 用户没给模块英文名 → 标 `[需补 EN]`，不要瞎翻译
- 用户给了中英双语 → 保留双语
- 默认产出：中文为主、英文辅助（架构图惯例）

## 第七步：输出 structured-content.md

严格用这个模板（字段顺序固定，方便下游消费）：

```markdown
# Architecture: [主题] ([English Topic])

## Layout

- 类型: [layered-stack|flow-pipeline|hub-spoke|swimlane] [横向|纵向]
- 风格: [待用户选 / 建议]
- 图标: [启用/不启用]
- 选这个布局的理由: [一句话]

## Layers (top to bottom) / Stages (left to right) / Hub & Spokes

### Layer 1: [层名] ([English])
- Module A ([EN]): [描述]
- Module B ([EN]): [描述]

## Side Columns (optional)

### Left: [侧栏名]
- Item 1
- Item 2

### Right: [侧栏名]
- Item ...

### Bottom: [基座名]
- Item ...

## Relationships

- A → B: [关系说明] [(默认)/用户明说]
- A ↔ B: [关系说明]

## Notes

- [任何需要用户确认的假设]
- [任何缺失的信息]
```

## 抽取后自检清单（必做）

输出前过一遍这个清单，**任何一项不满足都要修或标记**：

- [ ] **每个层/模块都有出处**：能指回用户原文的哪一句（不能凭空造）
- [ ] **没有遗漏用户提到的模块**：把用户的原文再扫一遍，对照结构
- [ ] **关系不是全 `(默认)`**：至少尝试从原文找显式关系信号
- [ ] **侧栏归侧栏，主层归主层**：安全/监控类没被塞进主层
- [ ] **布局选择有理由**：不是无脑 layered-stack
- [ ] **不确定的地方都标了**：`[待确认]` / `[需补 EN]` / `(默认)`
- [ ] **层数合理**：2-7 层（layered），2-6 列（pipeline），≤8 spoke，≤5 泳道

## 流程图专属深化（仅 swimlane 布局）⛔

如果抽取的布局是 **swimlane（流程图）**，主线抽取完**不要直接生成**。流程图的主线通常是"快乐路径"（全是通过），缺判断分支、异常回退、边界阈值。

⛔ **MUST read [flow-detail.md](flow-detail.md) and执行分批追问**，在生成前补全：
1. 判定要不要追问（flow-detail §0 触发条件表）—— 含审核类步骤 / >5步 / 用户要"详细" → 必问
2. 识别 5 类缺口（判断分支/回退/阈值/并行/起止）
3. 分批追问，每轮 ≤3 个，最多 2 轮
4. 回填 structured-content（加菱形/回环/起止节点）
5. 复述补全结果给用户最后确认

跳过条件：用户已说全分支、或明确要"简单画"、或主线已完整（见 flow-detail §"何时完全跳过"）。

**这一步是把"步骤序列"升级成"真流程图"的关键。** 不追问直接画，出来的图会缺菱形决策和回退路径。

## 常见错误（反面教材）

### 错误 1：脑补模块

> 用户："我们有用户端、订单服务、数据库"
> ❌ 错误抽取：补了"支付服务""商品服务""缓存"——用户没说
> ✅ 正确：只抽三个，想加就问"是否还有支付、商品等服务？"

### 错误 2：把侧栏塞进主层

> 用户："系统分四层：应用、服务、数据、存储，还有安全和监控"
> ❌ 错误：把"安全"作为第五层、"监控"作为第六层
> ✅ 正确：安全和监控是横切关注点 → 左右侧栏

### 错误 3：关系全默认

> 抽出来 5 条关系全是 `(默认依赖)`
> ❌ 说明根本没去找显式信号
> ✅ 重扫原文找"调用/通过/异步"等词；找不到才标默认

### 错误 4：层数爆炸

> 抽出 9 层
> ❌ 架构图超过 7 层就看不清
> ✅ 合并相邻小层，或建议拆成两张图

### 错误 5：忽略时序选错布局

> 用户描述的是"先 A 再 B 最后 C"的审批流程
> ❌ 用 layered-stack（依赖关系语义）
> ✅ 用 swimlane（流程语义），追问"涉及哪些角色"

## 与用户的交互规范

抽取不是黑箱——完成后要**向用户汇报抽到了什么、哪些是推断的**，让用户确认/修正：

```
我从你的描述里抽出了这样的结构：

- 布局：layered-stack（你提到了"上下分层"）
- 4 层：[列出]
- 侧栏：[如有]
- 关系：[列出，标明哪些是默认推断]

有几处我不确定：
1. [模块 X] 你没说是独立模块还是 [模块 Y] 的子模块，我先按独立处理
2. 关系 [A→B] 我按架构惯例标了默认依赖，你是否要明确？

确认或修改后我就开始画图。
```

这样用户有机会在你画图前纠正，避免返工。

## 处理"信息不足"

如果输入实在太少（比如就一句"画个电商架构"），**不要硬抽**，而是主动追问：

> 电商架构范围很广，为了画准，能补充几点吗：
> 1. 是前端到后端全链路，还是只画后端服务？
> 2. 大概分几层？（如：接入 / 服务 / 数据）
> 3. 有没有要特别强调的模块？（如支付、推荐、搜索）
> 4. 风格偏好？（暗色科技 / 亮色 / 政务蓝 / 黑白论文）

**宁可多问一句，不要画错一张。**
